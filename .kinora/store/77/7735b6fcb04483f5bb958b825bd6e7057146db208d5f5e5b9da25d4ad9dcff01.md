# Spec — a node's own recipes are listed and started by name from any host

**Contract.** The manual entries in a node's own manifest (the one boot autostart
reads) are that node's recipes. A `recipes` call lists them: name, argv, cwd and
what each is for. A named start may say it means a node recipe; the node then looks
the name up in its own manifest instead of the caller's workspace manifest. Either
way the start passes the gate exactly as an ad-hoc start of the same argv would:
the recipe names a command, it does not grant one.

**Why.** Starting by name read only the caller's workspace manifest, as a path on
the target, so a node's own entries could neither be listed nor started from
another host. Agents had to know exact argvs written down outside kudo, and an argv
holding a store path broke on every rebuild. The earlier process manager's main
use was exactly this: a per-node list of named recipes an agent could query and
run.

**Rejected.** Falling back to the node's manifest when the caller's workspace does
not declare the name: which manifest a name means would depend on the caller's
directory. Skipping the gate for a recipe: the manifest declares, the node's rules
authorize (kino://a457400202f392b8f3cb8c1266e0e7a8b4ca92ed3cff07e1fcd54e1952442226 holds for recipes too).

**Escape hatch.** A node with no manifest lists no recipes; ad-hoc starts work as
before.
