# Spec — an interrupted large put resumes from saved state

**Contract.** When a put to a remote place goes up in parts, the local
working copy (moco
`moco:7d189e690068d0f7200fcdbb236afe6ab64b6ad6535c8a8a883c3f825b72c79a`) records the upload's id and every
finished part (number, size, tag) in its own local state as each part
lands. A put of the same key started again — after the app was killed, the
network dropped, or the device restarted — lists the parts the remote still
holds, sends only the missing ones, and completes. The saved state is only a
hint: the remote's list of parts decides, and a part whose bytes no longer
match is sent again. An upload left unfinished expires on the remote and is
forgotten locally; nothing is visible under the key until it completes.

**Why.** A multi-GB video from a phone over cellular may never finish in one
go; restarting from zero wastes the parts already paid for.

**Rejected.** Restarting from zero (simplest; large files from phones may
never land). Keeping the state in the remote (it is per-device progress,
and removal never travels over the wire).

**Escape hatch.** A place without resumable parts (a plain file server)
restarts the put; resume is a capability, not part of the trait's contract.

**Open.** How long an unfinished upload lives before it expires.
