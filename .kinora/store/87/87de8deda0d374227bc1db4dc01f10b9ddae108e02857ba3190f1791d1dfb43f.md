# Spec — every process is dual-channel: a human lens and a machine lens

**Contract.** A job may declare **two independent views of one output stream**, and
both are captured continuously; the consumer picks per read.

- **Human lens** — PTY-backed, either `terminal` (VT-faithful: the engine keeps a
  virtual screen, so the human sees the TUI exactly as it draws) or `logs` (an
  append-only ANSI line stream).
- **Machine lens** — *optional*: either `{ file, format }` (tail and parse a
  sidecar the process writes) or a stream parser. When absent, an agent read falls
  back to recent scrollback text.

**A job with a human lens runs under a PTY regardless of which lens is read** —
TUIs require one, and many tools change their behavior (colour, progress,
buffering) the moment they detect a pipe. **The machine lens is declared, never
inferred.** Lenses are orthogonal to lifetime class: a governed *one-shot* command
may request PTY capture for exactly the same pipe-detection reason.

**Chosen.** Declare both channels per job. The machine lens is what makes agent
reads cheap, and cheapness decides whether the agent uses the substrate at all: a
read costing tens of thousands of ANSI-redraw tokens is a read the agent learns to
avoid, which makes the supervisor dead weight. This generalizes a trick good
watching type-checkers already hand-roll — a rich TUI for the human plus a
machine-readable diagnostics sidecar for the tool.

**Rejected.** Inferring structure from arbitrary output — auto-structuring is a
research project, while a declared sidecar plus a format name is three lines of
config and always right. Also rejected: capturing only the channel a consumer
currently wants, which makes the other channel unavailable retroactively.

**Escape hatch.** A job with no machine lens is fully supported; the agent reads
scrollback text and pays the cost knowingly.
