# Spec — a job survives restarting the daemon that spawned it

**Contract.** Because a governed command can *restart its own daemon* (a deploy
does exactly this), the job must survive that restart, which means closing **both**
independent kill vectors — either alone is insufficient: (1) **service-manager
tree-kill** — tell the service manager to signal only the main process (systemd
`KillMode=process`; launchd `AbandonProcessGroup`) so children survive; (2)
**broken-pipe death** — capture child stdout/stderr to **files** (stdin from
`/dev/null`), so a child that kills the daemon (the pipe's reader) does not then die
of `SIGPIPE` on its next write. The honest terminal state of a self-restarting job
is **"outcome-unknown / killed-by-signal"**, and that **is** success.

**Chosen.** Unit-level kill-mode + file-backed stdio, which also fixes the same bug
for supervised dev processes. Report "outcome-unknown" truthfully and verify such a
job **out of band**, not from its exit code.

**Rejected.** `setsid` the child (changes session/pgroup but not the cgroup, so a
cgroup tree-kill still gets it); and wrapping each command in its own transient
cgroup scope (one-platform-only, threads env/cwd/argv through an extra wrapper, and
fixes only governed commands, not dev processes).

**Escape hatch.** When the owning daemon cannot confirm a child's exit code, it
says so ("outcome-unknown") rather than inventing a result or losing the job.
