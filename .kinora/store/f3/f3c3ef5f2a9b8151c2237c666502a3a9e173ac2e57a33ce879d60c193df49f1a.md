# The Process Manager — a design-intent brief

*Consolidated from the kara prototype's spec ledger after the process manager
converged onto the hub. Like the earlier briefs this is **intent + learnings for a
clean-room rewrite**, not code to port: what was chosen, what was rejected, and
why — so a fresh implementation can re-derive the design instead of inheriting its
accidents.*

**Scope.** Supervision of long-running *dev* processes — TUIs, watchers, dev
servers — for two audiences at once: an agent that acts, and a human who watches.

**Where it lands.** Three homes, one design:

- **`moco`** — the **engine**: the supervisor core. Owns processes, PTYs,
  sampling, the manifest, the state machine, the on-disk registry, port
  allocation. Links no transport and no UI framework.
- **`kudo`** — the **agent face**: a stdio MCP shim, a thin proxy, no state.
- **the hub** (brief 1) — the transport that makes the engine reachable from
  another machine and from the browser console.

This brief assumes brief 1 (**The Hub** — reverse-dial, nodes, connectors,
consumers) and brief 2 (**Agent-First Job Substrate & Governed Commands**). The
process manager is the *long-running* half of the job substrate; governed commands
are the *one-shot* half. They share the north star: **agent-first, human-aware —
one observable substrate, the human as a minimal-intervention viewer.**

---

## 1. The problem, stated precisely

Some dev processes are built for **human eyes**. A watching type-checker or a
bundler's dev server draws a full terminal UI; its value to a human is the visual.
Hand the same process to an agent's own background-task facility and that channel
is lost — so in practice these processes live in hand-managed terminal
multiplexer tabs, and every restart is a manual handoff no agent can perform.

Three concrete pains drove the design:

1. **The agent cannot restart what it cannot own.** "Restart the checker and read
   the new errors" required a human.
2. **A raw TUI byte stream is the wrong food for an agent.** It is enormous,
   ANSI-laden, and mostly redraw. Reading it to answer "are there compile errors?"
   is absurdly expensive.
3. **Nothing could answer "what is wedging this machine?"** A runaway compiler can
   freeze the whole box, and no component had a machine-wide view of the process
   set to point at the culprit.

There is also a fourth, quieter pain that turned out to be structural: **ports.**
Multiple checkouts of one repo each wanted a dev server, and the coordination was
a shell script doing `flock` + a state file + a cooldown window, with the chosen
port invisible to everything else.

> **Framing that paid off.** One process, **two audiences**. A well-known watching
> type-checker already hand-rolls exactly this: a rich TUI for the human *plus* a
> machine-readable diagnostics sidecar for the agent. The whole manager is the
> generalization of that one trick.

## 2. Shape: one core, three thin faces

         agent (MCP shim)            browser console
                │                          │
                └──────────┐    ┌──────────┘
                           ▼    ▼
                          the hub                 (brief 1: routing only)
                             │
                  ┌──────────┴──────────┐
                  ▼                     ▼
            node daemon             node daemon    (one per machine)
                  │                     │
            ProcessConnector      ProcessConnector  (one service lane)
                  │                     │
              the engine            the engine      (moco: owns processes)

Four load-bearing structural calls, in the order they were made:

### 2.1 One machine-global supervisor, not one per project

The supervisor owns **every** managed process across every project and every
worktree on the machine. Clients attach; clients never own processes.

- **Rejected: one supervisor per checkout** (the pattern the watching type-checker
  itself uses). Such an instance cannot see total machine load, so it can never
  answer "what is wedging this machine" or hold a machine-wide budget — and that
  question is *inherently* machine-global.
- **Consequence:** the supervisor **outlives every client**. Restarting the agent,
  or closing the browser, never stops a managed process. This is the property the
  whole thing is for.

### 2.2 The supervisor is a *connector on the node daemon*, not its own daemon

The first cut was a dedicated process daemon with its own unix socket and its own
wire protocol, auto-started by the first client that found none running. That was
**retired**: the node already runs exactly one daemon that multiplexes connectors
and reverse-dials the hub (brief 1). Process management became **connector #6**.

- **Rejected: a separate process daemon plus a bridge to the hub.** A second
  daemon per node is redundant and duplicates the transport.
- **Won for free:** cross-machine reach, browser reach, one transport, one
  liveness story, one deployment unit — and process management sits beside
  sessions/files as just another capability rather than a special case.

> **Learning — the strongest one in this brief.** The process manager was designed
> standalone (own daemon, own socket, own UI, own MCP shim) and then folded into
> the mesh. Folding it in deleted *more code than it added*: a daemon, a socket
> protocol, a web server, and a standalone SPA all disappeared. **Design the
> capability, but host it on the daemon you already have.** If you are writing a
> second daemon for the same machine, stop and ask what the first one is missing.

### 2.3 The core is transport- and consumer-agnostic

The engine links **no** MCP SDK, **no** web framework, **no** transport. It
exposes a library API; the connector is a thin adapter over it. Adding a consumer
requires no change to the core.

- **Rejected: baking the MCP or HTTP protocol into the engine.** That couples the
  reusable heart to one caller.
- **Why it mattered concretely:** this is the *only* reason the design survived
  the standalone→connector migration in §2.2 with the core untouched, and the only
  reason it is portable at all. **This constraint is the deliverable.** If `moco`
  keeps one rule from this brief, keep this one.

### 2.4 Ownership is the workspace (the git worktree root), not the session

A **workspace** is identified by its canonical git worktree root (falling back to
canonical cwd when not a repo). Sessions are ephemeral clients that *attach*.

- **Rejected: per-session ownership.** A session restart would orphan or kill a
  dev server, and two sessions in one checkout would see divergent process sets.
- **Contract:** names are unique *within* a workspace; the fully-qualified id is
  `workspace:name` (so each worktree may define its own `check`). Ending or
  restarting a client never stops that workspace's processes.

There is a **second scope** beside `Workspace`:

- **`System`** — declared in a node-level manifest (`$XDG_CONFIG_HOME/<tool>/processes.toml`),
  **cwd-independent** (it runs a binary; cwd defaults to `$HOME`), unique by name,
  tied to no repo. This is where **node daemons themselves** live.
- **Rejected: keying system daemons to a synthetic repo workspace.** It couples a
  node daemon to a checkout that may not exist, and blocks running a prebuilt
  binary as a daemon with no working tree at all.
- The console groups system processes separately, so infrastructure is visually
  distinct from a repo's dev processes.

## 3. Dual-channel: the human lens and the machine lens

Every managed process is **dual-channel**, declared per process:

- **Human lens** — PTY-backed. Either `terminal` (VT-faithful: the manager keeps a
  virtual screen so the human sees the TUI exactly as it draws) or `logs`
  (append-only ANSI line stream).
- **Machine lens** — *optional*, and what makes agent reads cheap. Either
  `{ file, format }` (tail + parse a sidecar the process writes) or a stream
  parser. When absent, the agent falls back to recent scrollback text.

Rules learned the hard way:

- **Processes run under a PTY regardless of which lens is read.** TUIs need one;
  many tools also change behavior (colour, progress) when they detect a pipe.
- **The machine lens is declared, never inferred.** Auto-structuring arbitrary
  output is a research project; a declared sidecar+format is three lines of config
  and always right.
- **Both channels are captured continuously**; the consumer picks per read.

> **Learning.** "Give the agent a cheap structured view" is not an optimization —
> it decides whether the agent uses the tool at all. If reading a process costs
> tens of thousands of tokens, the agent avoids it and the manager is dead weight.
> The machine lens is the feature.

## 4. Declaration, hot reload, and failing loudly

Processes are declared in a checked-in **per-workspace manifest** at the workspace
root, with **ad-hoc spawning** as the escape hatch.

    [proc.check]
    cmd          = "…"                                  # run via sh -c
    human_view   = "terminal"                           # terminal | logs
    machine_view = { file = ".diagnostics", format = "…" }
    restart      = "on-failure"                         # never | on-failure | always
    autostart    = "session"                            # manual | boot | session
    limits       = { cpu_pct = 400, mem_mb = 8192 }     # advisory (see §7)

    [proc.dev-server]
    cmd       = "serve --port $MOCO_PORT"               # ordinary shell expansion
    port      = "auto"                                  # "auto" | <int> | absent
    worktree  = "each"                                  # each | main-only
    hosts     = ["workstation"]                         # allow-list; absent = anywhere

- **Rejected: purely dynamic** (every process re-specified at runtime) — nothing
  reproducible, and the agent must re-describe each process every time.
- **Rejected: manifest-only** — too rigid for exploratory work. Ad-hoc specs take
  the same shape, unpersisted.
- **Rejected: a bespoke config language** — TOML for the prototype.
- **Omitted from v1: file-watch auto-restart.** The processes worth managing
  already self-watch.

**The manifest is re-read on every `start` *and* every `restart`.** Both of these
were bugs found in use, and both are worth building in from day one:

- **Hot reload on `start`** was there from the beginning.
- **Hot reload on `restart`** was **not**. Restart respawned from the spec cached
  at first start, so editing the manifest and hitting restart silently ran the
  **old** config (a port change reverted itself; stop→start was the only reliable
  reload, which nobody would guess). Fix: restart re-reads the manifest, re-resolves
  the port for the new spec, swaps spec+port into the live handle, and then reuses
  the *existing* respawn path — so the delicate generation/supersede-monitor logic
  is shared, not duplicated.
  - Boundary: system-scope, ad-hoc, and adopted processes have no manifest entry
    and keep the cached-spec restart. Restart does **not** re-run the admission
    gates of §6 — it acts on an already-admitted process.

### A parse error must never degrade to an empty manifest

The original loader did the equivalent of `load(root).unwrap_or_default()`. One
invalid field therefore voided the **entire** manifest: the workspace vanished
from the process list and every start failed with `no process named <name>
declared in this workspace` — blaming the *process name* for a *file-level parse
error*. One typo silently disabled a whole workspace and pointed the operator at
the wrong thing. It cost a real debugging session.

- **A genuinely missing manifest stays a no-op** (`NotFound` → empty is correct:
  nothing is declared).
- **A real parse/IO error surfaces as a failed outcome naming the parse failure.**

> **Learning, generalizable well past this feature.** `unwrap_or_default()` on
> *configuration* is a latent misdirection bug. "Absent" and "broken" are
> different states and must produce different messages. Any place a default
> silently substitutes for a parse failure, the eventual error message will accuse
> the wrong component.

## 5. Lifecycle: two orthogonal fields, and *who* acts

The single most clarifying schema decision. Two fields that are constantly
conflated:

| Field | Question it answers | Values |
|---|---|---|
| `autostart` | **When is it first started?** | `manual` (default) · `boot` · `session` |
| `restart` | **What happens when it exits?** | `never` · `on-failure` · `always` |

They compose: a node daemon is `boot` + `always`; a dev checker is `session` +
`on-failure`; a one-shot is `manual` + `never`.

- **Rejected: overloading `restart = always` to also mean "start automatically".**
  It conflates first-start policy with crash policy, and makes "start once at
  boot, never restart" inexpressible.
- **Rejected: a bare `autostart: bool`.** It cannot distinguish the two triggers —
  and the triggers have **different actors**, which is the real point:

**`boot` is the daemon's job. `session` is the agent's job.**

- On startup the daemon loads the **system** manifest and starts every `boot`
  entry, honoring its restart policy thereafter.
- **Workspace manifests are deliberately not scanned at boot.** The daemon does
  not know every repo on the machine, and walking the filesystem for manifests is
  unbounded and surprising. **Rejected** explicitly.
- Instead the **agent** runs an idempotent **ensure** at session start: list the
  current workspace, start any `session` entry not already running. Ensure never
  stops or restarts anything, so it is always safe to run.
- Mechanism for ensure was **skill instruction** (the agent is told to do it); a
  session-start *hook* invoking a CLI entry point is the more robust follow-up.

> **Learning.** Naming the *actor* per trigger is what made this clean. "Autostart"
> as one boolean hides the fact that two different components, at two different
> times, with two different sources of truth, are doing the starting.

## 6. Surviving a restart: detached state on disk

Originally the registry was one daemon's in-memory map — so it died with the
daemon, taking the processes with it. The fix is the substrate for everything
multi-daemon.

**The registry is node-level state on disk**: one JSON file per process under
`$XDG_RUNTIME_DIR/<tool>/<node>/proc/`, written atomically (temp + rename).

**The detach trigger is `pty == false`** — opt-in, not universal. A detached
process is spawned with `setsid` (own session, no controlling tty), its
stdout/stderr appended to a **persistent per-process log file** (never a
daemon-owned pipe), and it is **not killed when the daemon drops** — only on an
explicit stop. Its scrollback *is* that file, so `tail` survives re-adoption for
free. A daemon started with a registry directory **re-adopts** live entries at
startup.

**Monitoring folds into the existing resource sampler** — no per-process waiter
thread, no per-process shim:

- **Own child** (spawned by this daemon run; we hold the handle): `try_wait` →
  reap → **exact exit code** → apply the restart policy precisely.
- **Re-adopted** (now init's child): `/proc` liveness, where liveness means *pid
  exists* **and** *its start-time matches the recorded one* — the guard against
  pid reuse. On death, **best-effort** classification: a requested stop settles
  `stopped`; any un-requested exit is treated as failure. This degraded,
  no-exit-code mode is **transient** — one restart makes it our child again and
  full fidelity returns.

Rejected along the way: an in-memory ring for detached output (the file already
persists it); killing children on drop (prevents detach outright); a per-process
supervisor shim (reintroduces a daemon-per-process — folded into the sampler
instead).

### The gap that is still open: who owns a `terminal` process's PTY

`logs`-view processes survive a daemon restart. **`terminal`-view processes do
not** — the PTY master is daemon-owned, so a VT-faithful process still dies with
its daemon, and cannot be attached from two daemons at once. For it to survive,
the PTY master must be owned by something that outlives any single daemon.
Candidates, undecided:

- **(a) a tiny per-process PTY holder** that owns the master + a screen ring and
  exposes attach (a mini-`abduco`). Keeps VT fidelity, portable — but reintroduces
  a small per-process daemon, the very thing §6 just removed.
- **(b) an external multiplexer** (`abduco`/`dtach`). Least code; adds a runtime
  dependency; fidelity is the tool's problem.
- **(c) a transient scope under the init system** + its journal. Survives, and
  gives cgroup limits for free — but the journal is line logs, so **VT fidelity is
  lost**, and it is Linux-only.

> **Learning.** The detach design cleanly solved the *easy* half and left the hard
> half honestly marked. Note that (c) would solve §6 and §7 together at the cost
> of §3's human lens — a real trilemma, not an oversight. Decide it deliberately
> in the rewrite; the shape of the answer determines whether a per-process
> component comes back.

## 7. Resource limits: monitor-first, advisory

Sample per-process CPU/RSS on an interval, retain a short history, surface it to
both faces, raise an event when a declared threshold is crossed — **but do not
throttle or kill.** Limit fields live in the schema **from day one** so
enforcement is purely additive later.

- **Rejected: kernel enforcement (cgroup v2) now** — needs delegation setup, is
  Linux-only, too much for a first cut.
- **Rejected: `nice`/rlimits** — coarse, and per-process rather than per-tree.
- **Why:** monitoring already answers the original question ("what is wedging this
  machine?"). Enforcement is a *different* feature wearing the same word.

Still unimplemented at the time of writing — limits remain advisory.

## 8. The port authority

The quiet win. Because the node daemon already owns the full process set, it is
the natural **port authority**, replacing the `flock` + state-file + cooldown
script.

- **One port range per node** (e.g. `10000–19999`), env-overridable. A *node*
  range, not a per-repo range.
- **The reserved set is derived from the shared on-disk registry, not held in
  memory.** At allocation time, scan the registry's **live** entries for ports in
  use (each entry's allocated port, plus declared fixed ports) and treat those as
  taken. **Rejected: a per-daemon in-memory reserved set** — invisible to a peer
  daemon sharing the registry, so two daemons would hand out the same port. Under
  multi-daemon the shared registry is the *only* correct source of truth.
- **`auto` allocation is sticky, then lowest-free.** If this exact
  `(scope, name)` previously held an auto port, and that port is in range and free
  (absent from the reserved set **and** it passes a live `bind()` probe), reuse it.
  Otherwise hand out the lowest free port passing both checks. The live probe is
  what respects ports held by processes the manager knows nothing about.
- **A node-level allocation lock** serializes scan→pick→persist across all daemons
  and entries, so two concurrent starts cannot pick the same free port. This is a
  distinct lock from the per-entry start/stop lock.
- **Fixed ports are reserved as-is** and excluded from the auto pool.
- **Reclaim is implicit, and there is no cooldown.** A port is "in use" only while
  its entry is live; a terminal (stopped/crashed) entry stops reserving it
  immediately. The old script's 180-second cooldown existed *only* because no
  process outlived the allocation — and **stickiness, not reservation, is what
  keeps a port stable across the gap.** Explicitly **rejected: holding a stopped
  process's port out of the pool**, which starves the range and reintroduces the
  very cooldown this removed.
- **Persist the assigned port on the registry entry** and thread it into the
  in-memory handle on re-adopt, so a re-adopting daemon keeps its port and peers
  see it in their scan.

**Delivery is env injection, not templating.** The assigned port reaches the
process as an environment variable — `MOCO_PORT` by default, overridable per
process via a `port_env` field. Because commands run via `sh -c`,
`cmd = "serve --port $MOCO_PORT"` just works.

- **Rejected: a `${port}` placeholder / templating engine over `cmd`.** `sh -c`
  already expands env vars; an interpolation layer buys nothing and creates a
  second, tool-specific escaping surface to get wrong.
- **Rejected: a bare `PORT`.** Too likely to collide with something the process or
  its own tooling already sets. **One prefix namespaces everything the manager
  injects**, now and forever.

**And the port is visible everywhere** — in the snapshot, the wire model
(`Option<u16>`), the console row (sortable/filterable), and the agent's list
output. **Rejected: leaving the port implicit** (present only in the child's
environment) — then nobody, human or agent, can tell which checkout's server is
on which port, which defeats centralizing allocation in the first place.

> **Learning.** Centralized allocation was worth it for a reason I did not
> anticipate: not the absence of collisions, but the **visibility**. "Which of my
> five servers is this?" stopped being a question.

## 9. Two more admission dimensions: worktree and host

Both are **start-time gates with informative refusals**, never parse errors — the
same shape, different axis. This shape is the reusable part.

**`worktree = "each" | "main-only"`** — a policy *within* workspace scope,
orthogonal to Workspace-vs-System.

- `each` (default) — every worktree of the repo runs its own instance, each with
  its own `auto` port.
- `main-only` — only the main working tree runs it. Detection reuses an existing
  boundary: the main tree's `.git` is a **directory**, a linked worktree's is a
  **file**.
- **A fixed integer port defaults `worktree` to `main-only`** (two worktrees
  cannot bind one port) unless set explicitly.
- **Rejected: modelling main-only as a System daemon** — these are repo processes;
  cwd matters and they live in the repo's manifest. **Rejected: running it
  everywhere and letting the OS reject the second bind** — trades a clear policy
  for noisy, racy failures.

**`hosts = [...]`** — an allow-list of **node names**, so *one* checked-in
manifest, shared across machines, can still pin a machine-specific server to one
box. This is the axis that let per-host multiplexer layouts fold into the manifest.

- **Matched against the node identity injected into the engine**, not the OS
  `hostname`. **Rejected: matching `hostname`** — it would make the engine call
  out to the OS and diverge from the mesh's canonical node identity, which is
  already plumbed in (as the port range is).
- Enforced in the engine's `start`, so **every** entry point (boot, session-ensure,
  explicit) is covered uniformly by one gate. Ensure silently skips a
  wrong-host/wrong-worktree process; an explicit start reports *why*.
- **Rejected: a per-host manifest** — defeats the point. **Rejected: a single
  `host` string** — a list is a strict superset at no cost.

Absent = runs anywhere. Both fields compose freely.

## 10. Hand-over: adopting a process the daemon didn't start

There is a bootstrap loop: the hub cannot be a daemon-started process, because the
management plane reaches the daemon *through the hub*. Yet the hub should be
visible in the process list like everything else.

**`adopt(scope, spec, pid)`** — factored out of the re-adopt path of §6, so both
share it: read the pid's `/proc` start-time, build a detached entry with no child
handle, insert, persist, spawn the `/proc` monitor. The already-running guard
applies. Two points make it more than a hack:

- **It is a lifecycle spectrum, not a separate kind.** `restart = never` + no
  command → **observe-only**: listed, state from `/proc` liveness, settles when the
  pid dies, its port joins the reserved set, and the daemon **never respawns it**
  (so it cannot fight a human restarting that process by hand). Give it a captured
  command and stop/restart start working too.
- **Entries are marked `external`** — a persisted flag (so re-adopt preserves it),
  surfaced on the wire model, distinguishing "handed over" from "daemon-started
  and detached".

Cross-process hand-over is a connector method: a peer that dialed in calls it to
register itself with the daemon that accepted it, and **the daemon hands over
itself** at startup.

- **Rejected: a parallel read-only "observed" subsystem** — observe-only is just
  adopt with `restart = never`; a second subsystem would duplicate the monitor,
  registry, and liveness machinery re-adopt already has.
- **Rejected: making the hub a daemon-started boot process** — circular, and it
  would force the hub into the packaged toolset. The goal here is *visibility*, not
  supervision.

> **Learning.** "Observe-only" falling out of an existing spawn path as a
> *parameterization* (`restart = never`, no command) rather than a new concept is
> the cheapest kind of feature there is. Look for that shape before adding a mode.

## 11. Access policy: read-all, write-own — and tombstones

**Reads are machine-global; writes are scoped to the caller's own workspace.**

- Read operations (list, tail, stats, screen, search) default to global — so *any*
  session can answer "what is wedging this machine".
- Mutations (start/stop/restart) resolve a bare name against the caller's
  workspace; a foreign fully-qualified id is **refused with a clear error**, never
  silently retargeted.
- **Rejected: cross-workspace writes** — convenient, and lets one session kill
  another checkout's dev server by accident. **Rejected: hard isolation** — loses
  the global read that motivated the whole thing.
- **The human console is the deliberate carve-out**: it is the one place for global
  human action (hand-kill a foreign process).

**Terminal entries linger, and clearing them is explicit.** A process that exits
stays in the registry as `stopped`/`crashed` so its fate is visible.

- **Clear removes only terminal entries** and returns the count. It never signals
  anything and never removes a live entry (stop it first).
- Scope follows the same split: the agent clears **its own workspace**; the console
  clears **globally**.
- **Rejected: auto-pruning.** A crashed process must linger so you can see *that*
  it died and read its last output. **Rejected: clear also killing running
  processes** — tombstone cleanup and kill-all are different verbs and conflating
  them is dangerous.

## 12. The agent face (→ `kudo`)

**A stdio MCP shim, launched per session, holding no state.** Its cwd *is* the
workspace key — the session's project directory comes for free, so workspace
identity needs no configuration at all.

- **Rejected: one shared HTTP/SSE MCP endpoint.** Every session would then have to
  *announce* its workspace; nothing carries cwd for free and identity becomes
  manual config.
- The shim is a pure proxy; all state lives in the daemon.

Tool surface, deliberately small: `list` · `start` / `start_adhoc` · `stop` /
`restart` · `tail` (last N scrollback lines) · `screen` (the faithful VT screen of
a terminal-view process) · `snapshot` / `stats` (state+pid+resources / sample
history) · `clear`.

### Two revisions worth inheriting

**(a) The shim went from local-direct to hub consumer.** The first decision was
that the agent calls its *own* node over a local lane — no hub hop, so local
control does not depend on the hub being up. That was **superseded**: once a node
can run more than one daemon (a stable one and a dev one), and once other nodes
exist, the hub *is* the natural router. The shim became a hub consumer, targeting
a node by tag, with a **per-request** link override for when the environment
matters (e.g. starting dev processes on the daemon that carries the dev toolchain).
The hub routes node→daemon, defaults to stable, and **falls back** to stable when
the requested one isn't registered.

- Accepted cost: the agent now needs the hub. Tolerable because during a session
  the hub is up and the daemons reconnect forever (brief 1, §2.1).
- **Rejected: a static per-project target in config** — the override is
  *per-request*, which keeps the manifest machine-neutral.

**(b) One multi-host shim; per-node shims deleted.** For a while there was a shim
per machine — the same binary, pinned to a different default node. That **triples
the tool surface the agent sees** (three `list`s, three `run`s…) for **zero**
capability, since the multi-host `node` argument already reaches every machine.
Exactly one shim is wired per workspace; cross-node reach is an argument, not
another server.

> **Learning.** Agent tool surface is a scarce resource and duplicated tools are a
> real cost, not just clutter — every near-identical tool is a chance for the agent
> to pick the wrong one. One parameterized tool beats N pinned ones, always.

## 13. The human face (the console)

Two levels, and the second one is the interesting decision:

- **Per-node process module** — the process table for one machine: state, pid,
  CPU/mem, **port** (sortable), the human lens (VT screen or log stream), and the
  global "clear stopped" action.
- **A cross-node dashboard**, peer to the node browser, built **only on connectors
  that already exist** — no new backend capability:
  - node/daemon discovery from the hub's registry → which machines are connected;
    reachability sampled **client-side** into a bounded ring for uptime sparklines.
  - one process-list lane per daemon node → that machine's processes, rolled up
    (running / crashed / restarts + worst class).
  - Roles are **derived** from the connector set, not a backend field.
  - Presentation is a **compact per-host rollup card** — a worst-health dot, one
    rollup line, a sparkline — plus a summary bar. The full process table stays
    one level down.
- **Rejected: a new backend health capability** (host CPU/disk/mem). The
  node-liveness and per-process signals already existed; adding a backend for the
  overview would have broken the "this is a UI shell" boundary. Host-level metrics
  can come later, additively.
- **Rejected: health as a per-host module** — it is inherently cross-node, so it is
  a top-level view.
- All scoring (role, rollup, thresholds, spark points, uptime) is **pure and
  host-tested**; only rendering is browser-side.

> **Learning.** The dashboard was built entirely by *aggregating existing
> connectors client-side*. Reach for that before adding a backend endpoint — the
> answer is often already on the wire.

## 14. Errors as a first-class feature

A recurring theme across both this brief and brief 2: **an unactionable error
costs a full human round-trip**, which is precisely the cost this whole system
exists to remove. Two concrete rules earned their place:

- **A failed spawn names the binary and the PATH it was searched on** — `binary
  '<argv0>' not found on PATH: <effective PATH>` instead of `No such file or
  directory (os error 2)`. The effective PATH is the daemon's real one, so the
  message shows the actual search path rather than a guess. Other spawn errors
  still name the program. It never prints any environment value but `PATH`.
  - **Rejected: probing PATH before spawn to pre-empt it** — that is preflight's
    job (brief 2), a separate opt-in check. The spawn path reports what *actually*
    failed.
- **A refusal says which gate refused and why** — wrong host, main-only in a
  linked worktree, foreign workspace, already running. Never a silent skip on an
  explicit request (though ensure *does* skip silently — different caller, correct
  difference).

> **Learning.** Budget error-message design as a feature, not polish. The
> degrade-to-empty bug (§4), the stale-restart bug (§4), and the opaque spawn error
> all cost multi-attempt debugging sessions, and all three were *message* failures
> as much as logic failures.

## 15. Status, and what I would do differently

**Converged and working:** engine hosted as a connector on the node daemon; the
agent driving any machine through the hub with one shim; one console managing
every node with per-node modules plus a cross-node dashboard; on-disk registry
with re-adopt; the port authority; worktree/host admission gates; hand-over.

**Retired along the way:** a standalone process daemon, its unix socket, its wire
protocol, a standalone web server, a standalone SPA, per-node MCP shims, and the
port-picking shell script. Every one of these was replaced by something the mesh
already had.

**Open:**
1. **Cgroup enforcement** — limits are still advisory (§7).
2. **PTY ownership for terminal-view processes** — the honest gap (§6).
3. **Browser-side reconnect resilience** in the console.
4. **Session-ensure as a hook** rather than an instruction to the agent (§5).

**If I rewrote it from scratch:**

- **Start at the connector, not the daemon.** Two thirds of the retirements in this
  brief are the standalone version being deleted. Build the engine agnostic (§2.3)
  and host it on the daemon that exists.
- **Put the registry on disk on day one.** In-memory-first forced a redesign of
  monitoring, restart classification, *and* port allocation. Everything
  interesting about §6 and §8 follows from "the registry is shared, durable node
  state".
- **Design the two lenses and the two lifecycle fields before writing the state
  machine.** The schema decisions (§3, §5) were the cheap ones with the largest
  reach; the bugs came from schema shortcuts (`unwrap_or_default`, cached spec),
  not from the supervision logic.
- **Decide the PTY-owner question early**, because option (c) collapses §6 and §7
  into one solved problem at the price of §3, and that trade should be made
  deliberately rather than discovered late.
