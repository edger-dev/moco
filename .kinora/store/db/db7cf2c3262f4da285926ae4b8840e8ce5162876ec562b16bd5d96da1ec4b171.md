# Spec — the screen is folded as output goes past, not replayed on demand

**Contract.** A terminal-lens job's screen is maintained **incrementally**: the
same pump that writes the job's capture feeds a VT parser held for the life of
the job, and a screen read returns that parser's visible grid. The capture is
replayed through a throwaway parser only where no live fold exists — a logs-view
job, or a terminal job re-adopted after the daemon that owned its pty died — and
the reply says which of the two it is.

Only the **visible grid** comes back. Scrollback is what `tail` is for, and
duplicating it here would undo the saving that justifies the lens.

**Why folding beats replaying.** Replay looks simpler and is wrong in a way that
is hard to see. The capture is bounded
(kino://f3c3ef5f2a9b8151c2237c666502a3a9e173ac2e57a33ce879d60c193df49f1a §6), so
a job that paints a banner once and goes quiet loses that banner the instant
compaction reaches those bytes — and the reported screen then disagrees with the
actual terminal, with nothing to signal it. Folding live means **the state
outlives the bytes it came from**. It is also O(1) per read instead of
re-parsing megabytes each time.

**Why it is worth having at all.** A progress bar that rewrites one line with
carriage returns is thousands of superseded frames in `tail` and a single line
here. This is the same economy as the machine lens: an *answer* rather than a
stream. `tail` structurally cannot say "what does it look like now".

**The grid is one number, not two that agree.** The job is told the terminal
size through the pty's winsize, and the parser renders at that same size. If
they diverged, every long line would wrap where the job never wrapped it and the
screen would be a plausible-looking fiction. A pty allocated with no winsize
hands the job zeros, so the size must be set explicitly — a job asking gets 0x0
and either refuses to draw or invents its own.

**All three descriptors are the pty**, not just the two that draw. A program
asking whether it is on a terminal overwhelmingly asks about stdin. The
consequence is stated rather than discovered: a job reading stdin **blocks**
rather than seeing EOF, exactly as it would at a terminal with nobody typing.

**Rejected — replay on every read.** See above; it is silently wrong once the
capture is bounded, and the bound is not optional.

**Rejected — persisting the fold.** A live pty already does not survive a daemon
restart (kino://<pty-durability>), so persisting the screen would preserve a
picture of a terminal that no longer exists. The replay path covers the
re-adopted job honestly, labelled as reconstructed.

**Rejected — returning scrollback as well.** It reintroduces exactly the cost
the lens exists to remove, and `tail` already serves it with resumable offsets.

**Escape hatch.** The `Replayed` source is always available and always honest,
so a caller that distrusts the fold can compare it against the retained capture.
