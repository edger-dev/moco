# Spec — the job registry is durable node state on disk, from day one

**Contract.** The registry is **node-level state on disk**, not one daemon's
in-memory map: one record per job under a node-scoped runtime directory, written
**atomically** (temp + rename). It is shared by every daemon on the node, so a job
id must be **stable across a daemon restart** and **non-colliding between daemons**
— a per-process counter is not a job id. A daemon starting against an existing
registry directory **re-adopts** its live entries.

**A daemon dropping never kills a job.** Only an explicit stop signals a child.
Detachment rides the mechanism already specified in
kino://0119d16e256891de4a71a14418f59c33419207f49792e58001639f8cbef567a6 —
unit-level kill-mode plus **file-backed stdio** — so a job's scrollback *is* its
persistent file and `tail` survives re-adoption for free.

**Monitoring folds into the existing resource sampler** — no per-job waiter thread,
no per-job supervisor shim:

- **Own child** (spawned by this daemon run; the handle is held): `try_wait` → reap
  → **exact exit code** → apply the restart policy precisely.
- **Re-adopted** (now init's child): liveness means *the pid exists* **and** *its
  recorded start-time matches* — the guard against pid reuse. Classification is
  best-effort: a requested stop settles `killed`; any un-requested exit is a
  failure. With no exit code available the terminal state is **`outcome-unknown`**,
  reported honestly. This degraded mode is **transient** — one restart makes the job
  our child again and full fidelity returns.

**Chosen.** On-disk from the first line of the substrate. Building in-memory first
forces a later redesign of monitoring, restart classification, **and** port
allocation, because each of those needs the registry to be shared, durable node
state; that redesign is the single most expensive mistake recorded in the source
brief.

**Rejected.** `setsid` as the detach mechanism — it changes session and process
group but not the cgroup, so a cgroup tree-kill still reaps the child; the source
brief proposes it, and
kino://0119d16e256891de4a71a14418f59c33419207f49792e58001639f8cbef567a6 already
rejects it for this reason. Also rejected: **killing children on drop**, which
prevents detachment outright; an in-memory ring for detached output, when the file
already persists it; and a per-job supervisor shim, which reintroduces a
daemon-per-job.

**Escape hatch.** When the owning daemon cannot confirm an exit code it says
`outcome-unknown` rather than inventing a result or losing the job.

**Explicitly open (not decided here).** Who owns the PTY master of a `terminal`-lens
job. `logs`-lens jobs survive a daemon restart; a VT-faithful job does not, because
the master is daemon-owned and cannot be attached from two daemons at once. The
candidates — a per-job PTY holder, an external multiplexer, or a transient init
scope whose journal loses VT fidelity — trade against each other and against the
human lens, and the choice determines whether a per-job component returns.
