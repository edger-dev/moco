# Spec — a large object is one object, with a derived BLAKE3 outboard

**Contract.** A file of any size is one object in a Place, keyed by the
BLAKE3 hash of its whole bytes (moco
`moco:a7089331ac0dff49deb5acc9afce92b2a9d8a9d5022f66af915f3a2332d6f447`); parts exist only inside a
transport (multipart puts, ranged gets). An object above 16 MiB also gets a
BLAKE3 outboard: the hash tree of its bytes, stored beside it and put by the
uploader. Any byte range of the object verifies against the object's own
hash with the outboard, so playback and spot checks need not read the whole
file. The outboard is derived: an outboard is checked by rebuilding it from
its object, a lost or rotten one is repaired rather than mourned, and it is
kept and removed together with its object. The caller still hashes first: a
large file is read once to hash it and build the outboard, then again to put.

**Why.** Identity stays the plain file hash, so inventories, keep-lists and
GC are unchanged and know no manifests. Media is rarely edited, so a whole
re-upload on edit is cheap next to a manifest layer every reader must follow.
BLAKE3 is already a tree, so verified ranges come at ~0.4% extra bytes (16
KiB groups) without changing any key.

**Rejected.** Fixed-size chunks plus a manifest (GC and inventories would
have to follow manifests). Content-defined chunks (compressed video dedups
poorly; most complexity). Outboards computed locally only (a phone would
read the whole file first). An outboard for every object (doubles the object
count for photos). Hashing while uploading to a temp key (no rename on S3:
a server-side copy per file, and a temp key breaks put-once).

**Escape hatch.** The threshold and the group size are recorded in the
outboard; a reader takes either. Chunks plus a manifest can still be added
for a class of files that is edited in place, as a new object kind.

**Open.** The outboard's key form: a key's last segment today names the hash
of its own bytes, so the outboard needs a form that names its object instead.
