# Spec — a terminal lens survives via a per-job PTY holder, and not yet

**Contract.** Two separable questions, answered separately.

1. **A `terminal`-lens job runs under a PTY owned by the daemon**, and that PTY
   **does not survive a daemon restart**. Its record, its id, its scrollback file
   and its ownership all do; the live terminal does not. This is the state of
   affairs today, adopted deliberately rather than by omission.
2. **When it is made durable, the mechanism is a per-job PTY holder** — a small
   process owning the master fd and a screen ring, exposing attach, tracked by
   the daemon through the ordinary adoption path. Not an external multiplexer,
   and not a transient init scope.

**Chosen — on sequencing.** Lens work does not depend on PTY durability, so it
is not held behind it. The **machine lens** is the piece the brief calls *the*
feature — the thing that decides whether an agent uses the supervisor at all —
and it is a declared sidecar file plus a format, needing no PTY whatsoever. A
`terminal` job dying with its daemon is annoying, not lossy: nothing that
persists is lost, and the fix is to start it again. Deciding durability first
would have blocked the valuable half behind a question it has no stake in.

**Chosen — on mechanism.** A per-job holder is the only candidate that keeps VT
fidelity, which is the entire reason the human lens exists. Three of its costs
have already been paid by work done for other reasons:

- the PTY mechanics exist and are tested (`moco-tty`: `openpty`, fork/exec,
  `setsid`, a reader thread);
- tracking a process the daemon did not start is
  kino://b8c4a03bb547f63b51ffd42c277d744e1c1b363f27182edc08363a16f52221db,
  already built, with `(pid, start-time)` liveness and an `external` flag;
- shipping a second binary is what a composition root is for.

**Rejected — a transient init scope.** It would solve durability *and* the still
-open resource limits together, which is genuinely tempting. But its journal is
line logs, so VT fidelity is lost and the terminal lens degrades into the logs
lens: it makes the feature durable by removing the feature. Linux-only besides.

**Rejected — an external multiplexer** (`abduco`, `dtach`). It saves less than
it appears. Answering "give me the current screen" requires a VT parser **on our
side whatever owns the master** — a multiplexer offers a socket for a *terminal*
to attach to, not a screen as text over an RPC. So the parser has to be written
either way, and the multiplexer only removes the fd-survival problem, at the
price of a runtime dependency every node must have installed.

**Rejected — the objection that a holder "reintroduces a per-job daemon".** The
lesson it appeals to
(kino://f3c3ef5f2a9b8151c2237c666502a3a9e173ac2e57a33ce879d60c193df49f1a §2.2)
is about a second **node-level** daemon duplicating transport, liveness and
deployment. A PTY holder has no transport, no registry and no liveness story of
its own — it is a process holding a file descriptor and a ring buffer. Treating
the two as the same thing is a category error, and it is what kept this question
open longer than it needed to be.

**Escape hatch.** Because the holder is adopted rather than special-cased, a
node that would rather use an external multiplexer can run one and hand the
process over: adoption does not care what created the pid.
