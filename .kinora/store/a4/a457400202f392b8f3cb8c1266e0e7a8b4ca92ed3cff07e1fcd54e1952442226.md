# Spec — the manifest declares; only the node authorizes

**Contract.** Two files, two owners, two different assertions:

| | declares | owner | trust |
|---|---|---|---|
| **manifest** (workspace or system) | the **definition** — argv, lenses, lifetime, `autostart`/`restart`, port policy, admission gates | the workspace; **agent-writable** | untrusted |
| **rule-set** (kino://eec764ea23113b4e48bfb2765ca0f1aa539f364dc7c94b04e3d4fd26be79fa1d) | the **authority** — which exact argv may run on this node | the node; human-only | trusted |

A manifest entry saying "run this" and the node saying "you may run this" are
**different assertions from different principals**. Therefore:

- **Starting a declared job passes exactly the same gate as an agent-proposed
  ad-hoc command.** Being declared earns no exemption. `start_adhoc` is the same
  code path with no manifest entry behind it.
- **The manifest is re-read on every `start` *and* every `restart`, and a restart
  therefore re-gates.** Re-read implies re-admit: the argv may have changed.
- A job whose exact argv has a **committed seed rule** auto-allows, so `ensure`
  starts it silently. A job with no matching rule **fails closed**; `ensure` skips
  it silently, while an **explicit** start reports *why*.

The resulting first-run flow is the coding-agent permission model already adopted
by kino://e1cb4151a2b6305296239a5afd3bbff7282b20abe377bad6531ee420be77c09b: a new
job → explicit start → pending → a human decides **allow always** once → an
exact-argv rule is written → every later session's `ensure` is silent and automatic.

**Chosen.** One uniform gate over one substrate, with the friction removed by
*seeding* rather than by *exempting*. The manifest declaring a job and the node
authorizing it are separable concerns, and separating them is what lets a
checked-in manifest stay zero-config while the trust boundary stays intact.

**Rejected.** Treating a checked-in manifest as trusted by construction. "Committed
to VCS" describes where a file lives, not that anyone reviewed it — and the agent is
actively editing that repo, so under a shell-string command it would obtain
arbitrary execution and under any command it chooses `argv[0]`. This is the
asymmetry against the node-owned seed rule-set and recipes
(kino://2c91815bf606d2e4e26e38d82d24b25aa85bfafd973fd3e3b6e103899a9d881b), which are
committed *where the daemon lives*, not in a checkout the requester controls. Also
rejected: exempting declared jobs from the gate to keep `ensure` prompt-free — the
seed layer already achieves that without an exemption. Also rejected: the source
brief's "restart does **not** re-run the admission gates"; combined with its own
fix that restart re-reads the manifest, that is a hole — edit the manifest, hit
restart, and a never-gated argv runs.

**Escape hatch.** A human who wants a whole class of declared jobs to run unprompted
seeds their exact argvs in the node's committed rule-set. The grant is then visible
in reviewed VCS, which is the point.
