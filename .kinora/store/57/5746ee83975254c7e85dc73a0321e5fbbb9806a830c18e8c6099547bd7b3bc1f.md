# Spec — the PTY holder owns the terminal, and files are how it speaks

**Contract.** A `terminal`-lens job is spawned as **`moco-pty-holder`**, a small
process that allocates the pty, execs the job on its slave, and holds the master
until the job ends. The holder is not the daemon's child in any meaningful
sense: it leads its own process group, writes the job's ordinary capture file,
and exits with the **job's** exit code, so every existing mechanism — `tail`,
compaction, liveness, restart policy, stop — keeps working without knowing a
holder exists.

Restarting the supervisor no longer closes the pty out from under the job. This
realizes the mechanism half of
kino://<pty-durability-is-a-per-job-holder>, which chose the holder and deferred
building it.

**Durability is opt-in.** With no holder path configured, terminal jobs behave
exactly as before — daemon-owned pty, dying with the daemon. A deployment that
has not installed the binary is not broken by its absence.

**Files, not a socket.** A socket needs the daemon listening at the moment the
holder has something to say, which is exactly what is not true across a restart.
A file is readable by whoever turns up next and needs no handshake. The holder
writes three things beside the capture: the rendered **screen**, the **job's
pid**, and the capture itself.

**The screen is written atomically.** The daemon may read it at any moment and
has no way to lock against the holder, so temp-and-rename is what makes "read
the screen" safe without coordination — a reader never sees half a frame.

**The screen flush runs on its own thread.** Flushing when the next chunk
arrives sounds equivalent and is not: a job that paints its screen and then goes
quiet blocks in `read` forever, so the screen would never be written at all —
and *drew once, then waited* is precisely the case the lens exists to serve.
A tenth of a second is faster than anyone reads and slow enough to be nearly
free against a TUI writing thousands of times a second.

**The job's pid is published, because the daemon cannot know it.** The daemon
spawned the holder, not the job. Resource samples must describe the **job**: a
holder is a read loop consuming almost nothing, so sampling it would report every
terminal job as idle whatever it was doing — the exact question resource
sampling exists to answer, answered wrongly.

**A stop reaches both.** The holder leads a process group containing the job, so
signalling the group stops the pair. A holder outliving its job would be a
leaked process per terminal job, forever.

**Rejected — a socket or any RPC.** See above; it fails at the one moment that
matters. It would also give the holder a transport, which is what would turn it
into the second node-level daemon this design rejected.

**Rejected — keeping the in-process fold as the source of truth.** It cannot
survive the daemon, which is the entire point. It remains as the fallback when
no holder is configured, and the reply still distinguishes `Live` from
`Replayed`, so a screen reconstructed from the retained capture is never
mistaken for one that was observed.

**Rejected — the holder owning scrollback in memory.** The capture file already
is the scrollback, it is already durable, and it is already bounded. A second
copy would be a second thing to keep true.

**Escape hatch.** The holder path is configuration, so a node can point at its
own build, and omitting it restores the previous behaviour exactly.
