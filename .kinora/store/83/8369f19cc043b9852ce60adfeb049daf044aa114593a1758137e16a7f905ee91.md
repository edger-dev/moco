# Agent-First Job Substrate & Governed Cross-Node Commands — a design-intent brief

*Consolidated from the kara prototype's spec ledger. Intent + learnings for a
clean-room rewrite, not code to port. Companion to "The Hub" brief — this layer
**rides on** the hub (it uses the hub's transport and node routing) but is not a
hub feature. The hub relays connectors; it knows nothing of jobs, rule-sets, or
approvals.*

---

## 0. The thesis: agent-first, human-aware

This is the load-bearing principle everything below realizes:

- The **agent is the operator.** It drives; it acts autonomously by default.
- The **human is a viewer** who can *always* observe and *rarely* intervenes.
- What makes both true at once is a single **job substrate**: every consequential
  action is an addressable, observable, controllable, durable **job** — never a
  blocking RPC that hides its state until it returns.

A job has five properties, and all five matter:

1. **An id** — addressable across a disconnect.
2. **Live status + output stream** — observable *while it runs*.
3. **A control handle** — killable / interruptible.
4. **A terminal record** — its result graduates into durable history.
5. **Detachment** — it outlives any one connection; a dropped lane or a daemon
   restart never loses it.

The unit of interaction is the job. A blocking call is at most **sugar** over
`start` + `wait`.

**The human console is a *projection* of the agent's job-world — one substrate, not
a parallel model.** The human watches the *same* job objects the agent operates on
(running / awaiting-approval / done, tail-able, across all nodes). One source of
truth; the console renders the substrate, it does not mirror it.

**Awareness is always-on; intervention is the human's only write, and is
minimized.** The human can observe anything anytime, but *writes* only at genuine
gates: **approve / deny (including edit-and-approve)** and **kill / abort**. The
default is the agent proceeds; the system is designed to need as *few*
interventions as possible.

### Why (and what was rejected)

- **Rejected: blocking RPC as the unit of interaction.** It hides run state until
  it returns, exposes no object for the human to watch, **loses its result on a
  disconnect**, and serializes the agent (no concurrency). It is the opposite of
  every property above. (Every `ConnectionClosed`-style failure the prototype hit —
  including a deploy that restarts its own host — traces back to blocking RPC.)
- **Rejected: a human UI with its own state model.** Two sources of truth drift;
  the human ends up watching a *simulation* of the agent, not the agent.
- **Rejected: human-in-the-loop by default.** Approval on every step makes the
  human a bottleneck, not a supervisor. Interventions are minimized by *governance
  policy* (read-only / auto-safe defaults, preflight, node-owned rule-sets), **not**
  by asking more often.

> **Learning.** This principle was *discovered late and retroactively explained
> everything.* The command-hardening work — read-only defaults, per-recipe env,
> preflight, auto recipes — all exists to *reduce interventions*; self-describing
> outcomes, timeouts, and detachment all exist to make jobs *observable and
> durable*. Naming the principle turned a pile of fixes into one coherent design.
> Start here next time, not at the end.

## 1. The first job type: a governed cross-node command

The motivating problem: an agent on one node (a locked-down container) needs to run
a specific command on a *different* node (e.g. trigger a dependency update on the
workstation, or run a tool that only works on the Mac) — replacing manual, unlogged
copy-paste between terminals.

A governed command **is a job** on the process registry, not a special RPC. It
reuses the whole substrate — the registry, the scrollback ring, tail/status,
detachment + re-adoption, the console module — and adds only the two things a plain
process lacks:

- a **governance gate** (the node-owned rule-set) evaluated *before* it spawns, and
- an **audit record** when it ends.

### The surface

- `start(argv, cwd, node) -> run_id` — evaluate the rule-set; if permitted, spawn
  **detached, file-backed** into the registry and return the id immediately; if it
  matches nothing, register the job as **pending-approval** and return the id
  *without spawning*.
- `tail(run_id, offset) -> (bytes, next_offset, status)` — incremental output +
  state; read by the console and, optionally, the agent.
- `wait(run_id) -> outcome` — block until terminal and return the result. This is
  the efficient collect: one call, **resumable after a disconnect** by id — not
  busy-polling.
- `kill(run_id)` — terminate; available to both the agent (it tailed a bad run) and
  the human (from the console).
- `run(argv, cwd, node)` — blocking **sugar** = `start` + `wait`, for quick
  commands, preserving a simple result shape for callers who want it.

**Approval is a job state**, not a side feature:
`pending-approval → running → done | denied | killed | timed-out`. The human's
decision transitions it; an **edited-argv** approval writes the corrected argv into
the job (a structured correction back-channel); pending jobs are simply *visible*
on the console. Notification, correction loops, and "why was this rejected" all
fall out of the state machine instead of being bolted on.

- **Rejected: model a remote command as a raw "run a shell string detached"
  process.** That path is unvalidated, fire-and-forget, no return value, no
  approval. Bolting governance onto it conflates one-shot request/response with
  long-running supervision.
- **Rejected: a command-only output runner separate from the process registry.** It
  duplicates the substrate. The whole value is that a command *is* a process with a
  rule-set in front — one registry, one tail/status/kill surface, one console.
- **Rejected: the agent busy-polling `tail` as the intended pattern.** The win is
  concurrency + `wait`/notification (fire N jobs, do other work, collect), not a
  poll loop. `tail` is for the console and optional progress checks.

## 2. The trust model (the part that must not bend)

### 2.1 Commands cross a host boundary as `argv`, never a shell string

A cross-node command is carried and executed as an **argument vector**
(`["tool", "sub", "--flag"]`) — never `sh -c "<string>"`. The daemon spawns the
program directly, so shell metacharacters (`;`, `&&`, `$( )`, `>`, backticks) are
**inert data**, not control flow.

- **Rejected: a shell string filtered by a prefix/pattern allow-list.** Pattern
  matching over a shell string is bypassable (`ok-cmd; rm -rf …`), so "secure"
  would be best-effort. Argv-only closes the injection surface **at the type
  level**, independent of what the rule-set happens to permit: the whitelist
  decides *which* argv may run; the argv shape guarantees it cannot *become*
  something else.
- `cwd` is validated to lie within a node-configured allowed root (no `..` escape),
  and the *resolved* cwd is echoed back (see §3).
- Pipelines/redirection are a non-goal; a recipe that truly needs one declares a
  wrapper program as `argv[0]`.

> **Learning.** "Argv, not shell" is *the* security decision. Everything else
> (rules, approvals) decides policy; this decides that policy can't be circumvented.
> It is also what keeps the audit trail meaningful — every recorded argv is exactly
> what ran.

### 2.2 The rule-set is owned by the *target* node and mutated only by a human

The allow/deny rule-set lives on, and is owned by, the **target node's** daemon. A
requesting agent may *propose* and *run* commands, but can **never** add, remove, or
widen a rule. Only a human, at the console, mutates it.

- Two layers over one matcher: a **git-committed seed** (reviewed in VCS) and a
  **daemon-owned mutable overlay** written *only* in response to human approval
  decisions.
- The agent surface is run + **read-only introspection** (see §3). There is **no
  agent-callable method that writes a rule.** Seeing what a human already granted is
  not the power to grant.
- **Fail-closed.** A proposed command matching no rule becomes *pending*. If no
  console is connected, or no human decides within a timeout, the run is
  **denied** — never run, never a silent hang. The agent gets an explicit "denied:
  no approver / timed out."

**Rejected: a rule-set the requester can seed or extend** (agent passes its own
allow-list, or auto-allow-on-first-use). That collapses the entire trust boundary
the feature exists to create. The requester is the *untrusted* principal; it must
not be able to escalate.

(Single human operator assumed; multi-user RBAC and remote mutation of another
node's rules are non-goals. Each node's rules are edited only where they live.)

### 2.3 Four approval verdicts; "always" writes an *exact-argv* rule

When a proposal matches no rule, the human is offered four verdicts, modeled on a
coding agent's own permission prompts:

- **Allow once** → run this instance; write nothing.
- **Allow always** → append an **allow** rule matching this **exact argv on this
  node**, then run.
- **Deny once** → reject; write nothing.
- **Deny always** → append a **deny** rule (exact argv on this node), then reject.

Deny beats allow on a match. The "always" verdicts are how the living whitelist
grows.

**Rejected: broad "program-only" or "prefix" auto-scoping on approval.** Allowing
one invocation of a tool must not permit every invocation of it. **Exact-argv**
keeps each standing grant deliberate and the audit legible — every standing allow
is a thing a human explicitly chose, verbatim. Recurring *parameterized* commands
are handled by a committed seed recipe, not by widening a click.

### 2.4 Recipes: parameterized, env-carrying, and the ssh-agent lesson

A committed recipe expresses its command as argv, optionally with validated bound
parameters, and may carry:

- **An `env` overlay** — a key/value table layered onto the command's environment,
  so a recipe that needs a specific `PATH` (or any var) declares it in *reviewed
  VCS* instead of the agent smuggling it through a shell string. Precedence: daemon
  env → ssh-agent env → recipe env (recipe wins ties). **Only a committed recipe
  carries env; the requester never supplies environment** (that would reopen the
  trust boundary). No secrets here — values are plaintext in the committed file.
- **`approval = auto | human`** — `auto` recipes run without prompting; `human`
  recipes prompt every time regardless of prior clicks.
- **`requires_ssh_agent`** — see below.
- **Variadic trailing args** for read-only recipes (a safe `{args...}` rest token),
  so "show me git log of X" doesn't need a fresh approval per argument.

**The ssh-agent lesson (a genuinely hard-won one):** a daemon running as a
per-user *service* does **not** inherit an interactive shell's `SSH_AUTH_SOCK`, so
a governed `git+ssh` fetch fails with a cryptic `Permission denied (publickey)`.
The fix that survived contact with reality:

- Before running, read `~/.ssh/environment` and layer `SSH_AUTH_SOCK` /
  `SSH_AGENT_PID` from it onto the command. Re-read it on **every** run, because the
  socket path is random per agent start (a stale value is worse than none).
- A recipe may set `requires_ssh_agent = true` to **fail loudly and actionably**
  ("start the agent on this node like so…") when no socket is available, instead of
  the cryptic auth error.
- Rejected alternatives, each for a concrete reason: a static `Environment=` in the
  unit (socket name is random), an `EnvironmentFile=` (read once, stale after an
  agent restart, wrong file format), a provisioned deploy key (the user already runs
  an authorized agent). Trust is unchanged: the boundary is still *which argv may
  run*, never the environment.

> **Learning.** The service-vs-interactive environment gap is invisible until a
> `git+ssh` command fails in production and works by hand. Budget for it: a
> long-running service sees a *different* world than your shell, and any recipe that
> reaches the network or a credential agent will trip on it.

## 3. Make the agent self-sufficient — minimize the human round-trips

The principle says "minimize intervention." Concretely, that meant giving the agent
enough **read-only** power to get a command right *before* spending a human's
approval:

- **Preflight** — `preflight(argv, cwd)` resolves, without queuing anything or
  running anything: the **disposition** a real run would get (allow / needs-approval
  / deny), whether `argv[0]` **resolves on the daemon's PATH** and to what absolute
  path, the **effective PATH** the daemon would spawn with, and the **confined
  resolved cwd** (or the confinement error). Most trial-and-error dies here, spending
  zero human round-trips. (Rejected: a `--dry-run` flag on the run call — a dry run
  must *never* be able to enter the pending queue or execute; a distinct
  always-read-only method keeps that unambiguous.)
- **Read the rules** — the agent can list the current allow/deny overlay (so it
  knows what's already granted). Read, never mutate.
- **Read the audit** — the agent can read past runs (cross-command learning: what
  worked, what got denied).
- **Self-describing outcomes** — a completed run echoes **where it ran** (the
  absolute, symlink-resolved cwd it was confined to) and **under what authority** (the
  verdict: auto-allow / allow-once / allow-always). The verdict returned to the
  caller is the *same* value written to the audit trail — one source of truth. The
  agent no longer guesses whether a relative cwd landed where it meant, or whether an
  unmatched command was auto-allowed or allowed-once. (Rejected: a separate
  "where did that run" round-trip — the provenance is free at run time.)
- **Legible spawn failures** — a "program not found" names the binary *and* the
  PATH that was searched, so the fix is obvious.
- **Bounded execution** — an execution deadline on the run plus a client-side RPC
  timeout, so nothing hangs forever on either side.

> **Learning.** Every one of these is a *human round-trip removed*. "Read-only
> introspection for the agent" is not a convenience — it is the mechanism that makes
> "agent-first, human rarely intervenes" actually hold in practice. If the agent
> can't inspect, it will spam approvals.

## 4. Durability: a job survives restarting the daemon that spawned it

Because a governed command can *restart its own daemon* (that is exactly what a
deploy does), the job must survive that restart. Two independent kill vectors —
**both** must be closed (either alone is insufficient; this was reproduced the hard
way):

1. **Service-manager tree-kill.** By default a service manager signals the whole
   process tree on stop/restart. Tell it to signal **only the main process**
   (systemd `KillMode=process`; launchd `AbandonProcessGroup`), so children survive.
2. **Broken-pipe death.** If the child's stdout/stderr are **pipes to the daemon**,
   then the moment the child kills the daemon (the pipe's reader), its next write
   gets `SIGPIPE` and it dies. Capture child output to **files**, not pipes (stdin
   from `/dev/null`). File-backed stdio removes the pipe, so the child survives
   killing its own reader.

- **Rejected: `setsid` the child.** It changes the session/process-group but **not**
  the cgroup, so a control-group tree-kill still gets it (fixes only the no-cgroup
  platform).
- **Rejected: wrap each command in its own transient cgroup scope.** Works, but is
  one-platform-only, threads env/cwd/argv through an extra wrapper (complicating the
  spawn diagnostic and env layering), and fixes only governed commands — not the
  supervised dev processes, which have the *same* bug. The unit-level kill-mode fix
  covers both.

The honest terminal state of a self-restarting job is **"outcome-unknown /
killed-by-signal"** — and **that is success**: the daemon that owned the job
restarted, so it cannot confirm the child's exit code and says so rather than losing
the command. Verify such a job **out of band**, not from its exit code.

> **Learning.** Detachment isn't a nice-to-have for long jobs — it's what lets your
> control plane operate on *itself*. The self-restart case is the acid test, and
> "I honestly don't know the exit code" is the *correct* answer, not a failure to
> engineer away.

## 5. Audit: every attempt is durable history

Every attempt — including every **denied** one — is written append-only and flows
into the same encrypted, never-delete backup pipeline as the rest of the system's
records, readable back and browsable in the console like any other historical
object. Output beyond a cap is truncated inline with a pointer to the archived full
record. (A searchable audit index, push notifications, and streaming-while-running
for the *human* were explicit v1 non-goals — the substrate makes them additive
later.)

## 6. The minimal shape to re-derive at home

1. Name the thesis first: **agent-first, human-aware, one observable job
   substrate.** Build the job (id · live output · control handle · terminal record ·
   detachment) before any specific feature.
2. The **console is a projection** of the job-world — one source of truth, never a
   parallel model.
3. Make the first real feature a **job**, not an RPC. A governed cross-node command
   = a process on the registry + a governance gate + an audit record.
4. Trust model, in order of importance: **argv not shell** (structural) →
   **target-node-owned, human-only-mutated, fail-closed rule-set** → **four verdicts,
   exact-argv "always"** → **committed recipes carry env/params; the requester never
   supplies environment.**
5. **Minimize human round-trips** with read-only agent power: preflight, read-rules,
   read-audit, self-describing outcomes, legible spawn errors, bounded execution.
6. **Durability**: close *both* kill vectors (kill-mode + file-backed stdio); treat
   "outcome-unknown" as the honest success of a self-restarting job.
7. **Audit everything**, denials included, onto a never-delete backup.

The transport and node routing all of this rides on is the **hub** — see the
companion brief.
