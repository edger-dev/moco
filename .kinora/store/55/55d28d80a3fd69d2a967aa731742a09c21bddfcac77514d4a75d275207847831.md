# Spec — the job is the unit of interaction, not the RPC

**Contract.** Every consequential action is an addressable, observable,
controllable, durable **job** carrying all five properties: (1) an **id**
addressable across a disconnect, (2) **live status + output** observable while it
runs, (3) a **control handle** (killable / interruptible), (4) a **terminal
record** that graduates into durable history, (5) **detachment** — it outlives any
one connection. A blocking call is at most **sugar** over `start` + `wait`.

**Chosen.** Model the unit as a durable job object. `run = start + wait` is a
convenience for callers who want a simple result shape, never the primitive.

**Rejected.** Blocking RPC as the unit of interaction: it hides run state until it
returns, exposes no object to watch, **loses its result on a disconnect**, and
serializes the agent (no concurrency). Every `ConnectionClosed`-class failure in
the prototype — including a deploy that restarts its own host — traced back to this.

**Escape hatch.** Callers who want request/response ergonomics use the `run` sugar;
they still get a job id underneath, so a dropped lane is recovered by `wait(id)`.
