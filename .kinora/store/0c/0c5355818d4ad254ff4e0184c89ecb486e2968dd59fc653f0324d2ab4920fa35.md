# Spec — a large sorted map is a content-defined tree of chunks over a Place

**Contract.** moco offers a sorted map (key → bytes) stored as a tree of
content-addressed chunks on any Place (moco
`moco:a7089331ac0dff49deb5acc9afce92b2a9d8a9d5022f66af915f3a2332d6f447`). Chunk boundaries are chosen by a
hash of the keys (a prolly tree), so the same entries always make the same
tree, whatever order they arrived in. A map is named by its root chunk's
hash. Writing changes only the chunks on the paths to changed keys; versions
share every other chunk. Diffing two maps (or three, against a base) skips
every subtree whose hash matches. A small map is one leaf chunk.

**Why.** A flat listing rewritten on every change costs O(n) per write and
keeps a full copy per version — about 38 MB per commit at 100k entries.
Content-defined boundaries keep two writers with the same entries
byte-identical, so put-once dedupes them and streams' forks stay rare.

**Rejected.** A fixed fan-out B-tree (its shape depends on insertion
history, so equal maps differ and fork). Checkpoint plus deltas (readers
replay, writers' deltas need folding). Sharding into many small maps (every
reader fans out).

**Escape hatch.** Chunk target size and the boundary hash are parameters
recorded in the root chunk; a map written with other parameters still
reads.
