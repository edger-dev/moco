# Plan — node recipes

**Task:** kino://9ba04ee753c1e23b79c522e2bdb632b81f048d57bb8a6f2d95d58d17ec728509

Two phases, each tests → implementation → fresh review → fixes.

1. **moco.** `ProcEntry.about` (optional). `Registry::recipes()` reads the
   node manifest (`load_node`) and keeps manual entries whose hosts admit
   this node. `Registry::start_recipe(name, caller)`: the entry must be
   manual, have a cwd and admit this node; it starts under the caller's
   scope (the console's is the system's) with the job named `node:<name>`,
   down the same `start` path (the gate runs there). `restart` of a job
   named `node:…` calls `start_recipe`. Wire: a `recipes` method with
   `RecipesReply`, and `StartNamedRequest.node_recipe` (default false, so an
   older caller still means its workspace).
2. **kudo.** The shim's `recipes` tool and `job_start`'s `node_recipe`
   argument, through the hub like the other job calls; the docs'
   process-manager tools page.

Not in this slice: recipe parameters (an entry is one exact argv); the
console listing recipes.

Phase 1 built and reviewed (23 Oct; 8b0299d tests, d5af229 implementation,
review fixes): `recipes` lists the node manifest's manual entries this node
admits; a named start with `node_recipe` starts one under the caller's scope
(the console's: the system's), named `node:<name>`, through `start` — the
gate and the allowed root apply as to any start. A restart keeps the job's
owner, whoever asks; a workspace manifest may not declare a `node:` name;
`recipes` is advertised in METHODS. Not handled, as in `boot`: a recipe with

a verdict like any start. Docs: deployment (the node manifest) and tools.
