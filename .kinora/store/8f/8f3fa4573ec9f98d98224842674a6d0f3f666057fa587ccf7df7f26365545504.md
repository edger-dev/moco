# Spec — a terminal job accepts input

**Contract.** A `Terminal`-view job accepts **input**: bytes written to its
terminal as if typed, through an `input` call on the wire naming the job and
the bytes. Typing is the **human's intervention**: only the console may type,
never a session, which could otherwise type past the approval its argv was
given. One input carries at most 4096 bytes (one atomic pipe write) and lands
whole or is refused whole; inputs reach the pty in the order they were
accepted. A job that is not a running terminal, or is **not reading its
input** (its queue or pipe is full), refuses input with a plain error and
never makes anything else on the node wait. Each job's audit record counts
the inputs it received and their bytes, never what was typed. Reading what
the job drew stays the `screen` call it is today.

Under the PTY holder, input goes through a FIFO beside the job's capture,
which the holder makes owner-only, reads and copies to the pty; only that
FIFO is a way in (never a symlink or a plain file at that path). It needs no
socket and survives a supervisor restart like everything else the holder
owns — the job's view is persisted, so a re-adopted terminal job still takes
input.

**Chosen.** Input as a wire call, so the console (through the hub) can type
into a pane: that is what taking over a worker means when the person is not
at the machine. A FIFO beside the capture keeps the holder small and
transport-free, as its own spec requires.

**Rejected.** A socket per holder (the holder spec rejected sockets: nobody
may be listening when one is needed). Attaching a local terminal (`tmux
attach`-style) as the only path (does not reach a phone or a browser).

**Escape hatch.** A local attach command can be layered on the same FIFO and
screen file later, for a person sitting at the node.
