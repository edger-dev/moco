# Finding — a job running as the daemon's user can plant a standing rule

Seen in review of the standing verdicts, 22 Oct. The overlay
(`standing-rules.styx`) lives in the registry directory, owner-only — but jobs
run as the daemon's own user, so an allowed job that writes files can replace
it, and its rules apply from the next read. The same holds for job records
and the audit file. That is a write path to the rule-set no human took.

Mitigations, cheapest first: refuse an overlay whose rules have no matching
`ApprovedAlways` / `RejectedAlways` audit record (the audit is in reach of the
same user too, so this only raises the bar); run governed jobs as a separate
user, so the daemon's state is out of their reach (the real fix); sign the
overlay with a key jobs cannot read. Until then, the seed (read-only, from
the Nix store) is the only rule source a job cannot touch.

Also from that review: `Verdict` gained four variants, so an older binary
cannot read records or replies that carry them — no rolling back across this
change on a shared directory.
