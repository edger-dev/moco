# Plan — the standing verdicts

**Task:** kino://612312235e76b1adb626c52a275a07b7be786d835bd63facdc9c250ece104687

One phase, tests → implementation → fresh review → fixes.

- The overlay is a `RuleSet` held by the registry beside its policy, behind
  its own lock, stored as `standing-rules.styx` (the seed's shape, fields
  escaped as job records are) in the registry directory; loaded by
  `with_policy` from the private directory and again by `with_dir`.
- `decide` with an *always* verdict reads the pending argv (the edited one for
  an edited allow), writes the rule unless the argv is already denied, then
  runs the *once* path. A failed write fails the decision and leaves the job
  pending, so the human can still choose once.
- Verdicts gain `StandingAllow`, `StandingDeny`, `ApprovedAlways`,
  `RejectedAlways`; the gate reports a standing rule apart from a seed one.
- Not in this slice: releasing other pending jobs with the same argv when an
  always-allow lands (each still asks); removing a standing rule (edit the
  file by hand, as an operator).
