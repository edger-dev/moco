# Spec — a config parse failure is never a silently empty config

**Contract.** Loading a declaration file distinguishes **absent** from **broken**,
and the two produce different outcomes:

- **Absent** (`NotFound`) → an empty declaration set. Nothing is declared, and that
  is correct and silent.
- **Parse or IO error** → a **failed outcome naming the parse failure** — the file,
  the position, and the offending field. It never degrades to an empty set.

No load path may use `unwrap_or_default()`, or any equivalent that substitutes a
default for a failed parse, on configuration.

**Chosen.** Fail loudly and specifically on broken configuration. The prototype's
loader degraded a parse error to an empty manifest, so one invalid field voided the
*entire* file: the workspace vanished from the process list and every start failed
with `no process named <name> declared in this workspace` — blaming the **process
name** for a **file-level parse error**. One typo silently disabled a whole
workspace and pointed the operator at the wrong component. It cost a real debugging
session.

**Rejected.** Treating "could not read it" as "there is nothing to read". Any place
a default silently substitutes for a parse failure, the eventual error message
accuses the wrong component — the failure surfaces far from its cause, wearing a
misleading name.

**Escape hatch.** A caller that genuinely wants best-effort loading asks for it
explicitly and receives both the partial result **and** the errors; the default
path never discards an error.
